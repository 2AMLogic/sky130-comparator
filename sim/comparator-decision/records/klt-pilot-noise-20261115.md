# Pilot note 2026-11-15 -- input-referred noise (`.noise`) as a `klt sim` request on the batch fleet (issue #221)

Not a ratified record: no `Record ID`, no new graded corner set beyond the one
pilot corner. It answers one question for #127: **can `run.py noise`'s ngspice
`.noise` analysis and its integrated-noise read-out be expressed as a `klt sim`
request, and does the fleet reproduce `run.py`'s number?** Answer: **yes to
both** -- but not through `.meas` cards, and with one workaround whose cost is
named below rather than hidden.

Follows the `kickback` pilot (`klt-pilot-kickback-20261106.md`, issue #211) and
the `regen` pilot (`klt-pilot-regen-20261114.md`, issue #220); same file-naming
convention that pilot established. `offset` and `reset` remain unattempted.

`status: "pass"`, all six measurements finite, zero corner diagnostics:

| Quantity | Fleet value | `run.py` baseline (record `20260922-065534-e084b55`) | Delta |
| --- | --- | --- | --- |
| Op point v(TAILP) | 0.1793541972999 V | 0.1794 V | match at the record's displayed precision |
| Op point v(OUTP1)=v(OUTN1) | 1.177188732304 V | 1.1772 V | match at the record's displayed precision |

| Output-referred `onoise_total` at v(OUTP1,OUTN1) | 1.202271390894e-03 V | (not stored in the record) | -- |

The baseline record stores four decimal places, so "delta" cannot be computed
tighter than its displayed precision -- the honest statement is **every
quantity the record stores is reproduced to that precision**, by a fleet run
on a different ngspice (46 -> 47) and PDK revision (`c6d73a35` -> `f6eeac7`).
Unlike the `kickback` and `regen` pilots, whose deltas had to be flagged
"indicative only" against unquantified environment drift, this measurement
shows **no visible PDK/ngspice-revision confounder at this corner**: nothing
moved beyond what the record's storage precision can express.

**Against the ratified bound, stated for completeness and legislating
nothing**: DR-002 ratifies Input-referred noise at <= 1 mV rms differential
(target) / <= 0.6 mV rms (stretch). The request carries the target itself as a
graded limit -- `inoise_diff_mv` `limits.max: 1.0` -- which returned
`status: "pass"`, `margin: 0.429552`; 0.5704 mV also sits under the stretch.
The pilot clears both bounds and re-opens no row: it is a lower bound by
construction (the loop break excludes the latch's regenerative-phase noise;
see the baseline record's methodology note), and a single-point pilot is not
the evidence that would re-grade the row anyway.

## How the read-out works, and what `run.py` does that the request replaces

`run.py noise` applies four post-processing steps after ngspice returns, and
**none of them can be a `.meas` card**: `_SUPPORTED_MEAS_TYPES` is
`{"dc", "ac", "tran", "sp"}` and `klt` rejects a `.meas noise` card before
ngspice runs ("ngspice has no `.MEASURE NOISE` analysis type") -- a
double lockout, since ngspice itself has no such form. `.noise`'s results are
plot scalars of its second result plot, visible to ngspice's control language
but not to the `.meas` machinery. Each step, and how the request reproduces
it with `let`/`print` expressions in the body's control block instead:

| `run.py` step after ngspice returns | Request equivalent |
| --- | --- |
| 1. Parse v(TAILP), v(OUTP1), v(OUTN1) from the `op` print | `let op_tailp = v(TAILP)` (+ outp1/outn1), then `print op_tailp op_outp1 op_outn1`. The **`let` alias is required**: the log harvester's `_MEAS_VALUE_RE` only matches `name = value`, and a printed `v(tailp) = ...` carries parentheses that never match -- without the alias the op nodes come back missing and the corner grades error. |
| 2. Parse `inoise_total` | The body block runs `noise v(outp1,outn1) Vinp dec 20 1000 1e+09 20` itself, then `print inoise_total onoise_total` -- the analysis's own plot scalars, in harvestable `name = value` form. |
| 3. Multiply by `sqrt(2)` for the differential estimate | Done **in-deck**, before printing: `let inoise_diff_mv = inoise_total*sqrt(2)*1000`. `klt` has no derived/expression measurement, so the unit conversion and the diff-pair doubling cannot be stated in the request. |
| 4. Compare against DR-002's 1.0 mV target / 0.6 mV stretch | The target becomes a **graded limit on the request itself**: `inoise_diff_mv` `limits.max: 1.0` (report `margin: 0.429552`, `coverage.nothing_checked: false`). The stretch 0.6 is not expressible as a second bound in this schema and is stated in this note instead. |

So: `klt` grades **printed scalars**, not `.meas` values, on this route.

**Route cost, stated rather than hidden**: the `.noise` analysis runs **twice
per corner** -- once in the body's control block (which must run the analysis
to make the scalars exist; a print-only body block runs before klt's analysis
and warns "vector inoise_total is not available"), then again in klt's own
control block. The committed log shows exactly that: three solver
initializations (`op`, body `noise`, klt `noise`). Cost here ~2 s of fleet
time (corner runtime 3.448 s in-corner, 12 s job elapsed). A pre/post-analysis
command hook or a derived-measurement field in the request would eliminate the
duplicate run and move step 3 into the request; filed as friction below.

`models_lib_comparison: "match"`, `models_lib_sha256 48de7c67...` -- the same
hash the `regen` pilot recorded for the `combined` library.

## Solver check

ngspice's KLU solver silently cannot run `.noise` ("Noise simulation is not
(yet) supported with 'option KLU'. Use 'option sparse' instead." --
`noise.py` carries this caveat where it builds the deck). `klt` writes the
corner's own `.spiceinit` from `options.ngspice_init`, so the repo's
`sim/spiceinit` `option klu` is **not** inherited on this route, and ngspice
defaults to SPARSE anyway -- but the request sets `option sparse` in both the
body block and `.spiceinit` regardless. The committed run's log states
**"Using SPARSE 1.3 as Direct Linear Solver"** at every solver
initialization and never KLU. (The log itself is not committed -- `*.log`
gitignore -- so this paragraph is the committed record of that check;
`corner.cir` and `.spiceinit` under `out-noise/` carry the `option sparse`
lines it reflects.)

## The dry-run false positive

`klt sim noise-request.json --dry-run` grades the request `valid` (1 unit,
`warnings: []`) but raises one preflight diagnostic:
`model_bin_range_preflight` on `XM_C1P`, "has w=4e+07u, at/above the ~100 um
per-instance width bin range". The device is `W=40` **um**; the preflight
reads the bare `W=` as metres and inflates it by 1e6. It is a **false
positive**: `status` stays `valid`, the fleet run passes,
`diagnostic_counts.corners_with_diagnostics` is 0, and ngspice never aborts
on a model bin. It appears in `dry-run-noise.json` and not in
`report-noise.json` (diagnostics `[]`). The sizing is the schematic's, taken
verbatim from the fragment -- not "fixed" here. Filed with the rest of the
route friction.

## Friction filed

[`2AMLogic/klayout-tools#5802`](https://github.com/2AMLogic/klayout-tools/issues/5802)
-- two generic gaps in one filing, described without this design's details:
(a) no request hook for a pre- or post-analysis control command and no
derived/expression measurement, so an analysis whose result is a plot scalar
rather than a `.meas` value can only be graded by smuggling a duplicate
analysis plus `print`s into the netlist body's control block, paying for the
analysis twice; (b) `model_bin_range_preflight` misreading a PDK's
micrometre `W=`/`L=` as metres and emitting a spurious at/above-bin-range
warning. AC 6's "not expressible" branch did **not** fire: the measurement
is expressible, via the workaround above.

## Caveats

- One PVT point (`tt`/27 C); other corners and the extracted DUT are out of
  scope, and the `run.py noise` baseline this pilot differences against only
  exists at this corner. `noise-tran` (the regeneration-inclusive campaign)
  is a different measurement and remains unattempted on this route.
- "Match at the record's displayed precision" is the tightest claim the
  baseline's four-decimal storage supports; a digit-for-digit ngspice-46 vs
  -47 or `c6d73a35` vs `f6eeac7` equivalence is *not* established, only that
  nothing moved past 0.5 in the fourth decimal place (and the op nodes past
  0.00005 V).
- The differential estimate is `sqrt(2)` x the single-ended figure -- the
  diff-pair noise-doubling approximation, named and flagged in the baseline
  record, not re-derived here. The lower-bound caveat (latch noise excluded
  by the loop break) carries over unchanged.
- The body is a snapshot: if `testbench/comparator_core.spice` or
  `_noise_sub_model_lines()` moves, regenerate it from `_noise_deck` rather
  than editing device lines by hand (snapshot provenance is stated in the
  body header).
- `run.py` was not touched; no ratified record, spec row, characterization
  report or `regen-*` artifact changed.
